# ADR 0010: The Studio's output is a project, and a project's output is a development package

**Status:** accepted · 2026-10-13

## Context
Until now the Studio ended in *Put it to work*: the AI employee it designed ran on the platform. The product owner no longer wants the platform to be where agents are built; they want the Studio to end in a **development package**, a zip a developer feeds into Claude Code to build the agent in whatever stack the project needs. The Studio should know everything in the company brain and design with it, the person should be able to open the brain during a design and pick assets by hand, and an agent design should be a **project** whose export is the package. The owner also wants to use the platform for their own work as an AI agent development company: projects, with any kind of thing and asset inside, used during development, and their own to-dos.

## Decision
- **A project is a table and a thing.** `projects` holds what the app needs (slug, owner, client, status, its channel, its assets, when it was exported); a thing of kind `project` in the brain holds what the company knows about it (links, timeline) and makes it searchable and nameable with "@". The two are kept in step: a rename or a status change goes to both; a same-name `project` thing that already exists is adopted rather than duplicated. The owner's brain person *leads* it and the client thing is linked *for_client*.
- **Export first; *Put to work* stays.** Every Studio conversation and interview can belong to a project (`studio_threads.project_id`, `builder_sessions.project_id`); the project's **Designs** are found through these keys and their AI employees through what the designs made, not through asset rows. The package is the project's main output; a design can still be put to work on the platform, so the demo and the ready-made AI employees keep working.
- **The package is a specification, not code.** `README.md` (how to use it with Claude Code), `CLAUDE.md` (what to build, the rules in the owner's words, the folder map, how to reach the live brain), `.mcp.json` (the installation as an MCP server, the key as `${EB_API_KEY}`, never its value), `project.json`, one folder per AI employee (`SPEC.md`, `definition.json`, the conversation or interview that designed it, `tests.md` from its tries), `brain/` (one Markdown file per thing with its links, grouped by kind, plus `things.json`), `data/` (tables with their schema and up to 50 sample rows, calculations, apps), `knowledge/`, `files/`, `connections/` (named actions, config keys and the **names** of secrets only) and `tasks/PLAN.md` (the build order, the open to-dos, the Studio's unanswered questions). Rendering is pure and deterministic (`packages/builder/src/dev-package.ts`); the server collects (`apps/server/src/dev-package.ts`). Sample rows mask personal fields as `[personal]` unless the data protection officer approved them; a calculation's code goes in for admins only, others get the rule in words. An asset the exporter may not see is left out and named in a warning, so the same project exports differently for different people.
- **The live brain for Claude Code.** The MCP server gains `company_search` and `company_open` (text results), so the development environment can look up what the package summarises; the package names them and the key variable.
- **The Studio inside a project** gets the project's summary and assets in its brief once, at the start of the conversation, and two tools of its own: `project_add_asset` (what it found in the brain that the AI employee will need) and `project_add_task` (what only the person can do). Its `look_around` carries the project live, so assets added later by hand reach it.
- **The project channel is an ordinary private channel** (visibility `participants`, no `about_id`), named after the project's slug, renamed with the project and archived when it is done or cancelled; a channel with an `about_id` is a built-in one and cannot be managed.
- **To-dos are new and one person's.** `todos` holds a person's own tasks (from a project, from the Studio, from their mail, written by hand), with a due date, a status, a source and a link back; `(user, source, source_ref)` is unique so a source never makes the same to-do twice. A to-do is not a `tasks` row (every task needs an AI employee) and not a work item (those are AI employees' questions). Nobody assigns to-dos to colleagues in this version.
- **Permissions.** Everyone signed in reads the projects and creates one; the owner, admins and managers change, add to or remove one. Designs are listed for every reader and opened by their owner or an admin, as today. Assets are checked against what the viewer may see when added. The open-mode and API-key viewers have no person, so they get no to-dos (409).

## Consequences
- The Studio has a second ending: *Export the package* beside *Put it to work*. A project's Package tab shows what the zip will hold, folder by folder, and each export is kept on the project and on the thing's timeline.
- Projects give the brain a place for the owner's own client work: a client, its processes, documents and data gathered once, used by every design for it, and handed to a developer in one folder.
- The package reflects the platform's model of an AI employee (job, duties, triggers, tools, approvals, knowledge) in words and JSON; it does not promise a runtime. Claude Code chooses the stack from `CLAUDE.md`.
- Not in this version: a code skeleton in the package, per-project permissions beyond owner and managers, to-dos assigned to colleagues or handed to an AI employee, a "project" reading in the Home box, mirroring the project channel to Teams or Google Chat.
